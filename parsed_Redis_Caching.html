Redis version-based caching: a simpler way to invalidate

Tag: Backend
Read time: 6 min

Caching is easy until data changes.

The first version of almost every cache looks reasonable:

Request
│
▼
Check Redis
│
├── hit ──► return
│
└── miss
│
▼
Database
│
▼
Cache result
│
▼
Return

That is the easy part.

The difficult question is:

what happens after a write?

In a multi-tenant backend with filtered lists, pagination, sorting, search, role-aware visibility, and multiple service instances, one logical dataset can produce a large number of cache keys.

For example:

dev:contacts:tenant-42:list:page-1
dev:contacts:tenant-42:list:page-2
dev:contacts:tenant-42:list:status-active
dev:contacts:tenant-42:list:owner-u123
dev:contacts:tenant-42:list:sort-createdAt-desc
dev:contacts:tenant-42:list:search-acme

Add combinations:

page
pageSize
sort
search
filters
owner
team
status
date range

and the keyspace grows quickly.

Then a contact changes.

Which keys are stale?

Potentially all list caches derived from that tenant’s contact dataset.

This is where our invalidation approach started becoming expensive.

The system could cache quickly but had to spend too much time discovering and deleting stale keys.

In the failure mode that pushed the redesign, invalidation was taking long enough to contribute to slow request paths and timeout behavior.

The cache had become a latency source.

That is the opposite of why it existed.

The first instinct: delete matching keys

A straightforward invalidation strategy is:

contacts updated
│
▼
find keys matching:
tenant-42:contacts:*
│
▼
delete all matches

At small scale, this feels fine.

The dangerous implementation is:

KEYS tenant-42:contacts:*

followed by:

DEL ...

I do not consider KEYS a production-safe invalidation strategy for a shared Redis workload.

It scans the keyspace synchronously.

As the keyspace grows, the operation can block Redis long enough to affect unrelated traffic.

The next improvement is obvious:

SCAN MATCH pattern COUNT 100

Unlike KEYS, SCAN is incremental.

Conceptually:

let cursor = '0';

do {
const [nextCursor, keys] = await redis.scan(
cursor,
'MATCH',
pattern,
'COUNT',
100,
);

cursor = nextCursor;

if (keys.length > 0) {
await redis.del(...keys);
}
} while (cursor !== '0');

That is much safer than KEYS.

And in an earlier stage of the design, moving to a SCAN-based invalidateByPattern(pattern) approach was the correct improvement.

But “safer than KEYS” does not mean “free”.

That distinction became important.

SCAN solved blocking, not discovery cost

Suppose a write invalidates:

dev:contacts:tenant-42:*

Redis still has to iterate through the keyspace to discover matching keys.

The application still has to:

  • maintain a cursor
  • perform repeated round trips
  • collect matching keys
  • issue delete operations
  • handle large match sets
  • wait for the process to complete or move it elsewhere

The operation is incremental, but it is still work.

If invalidation happens frequently, the system repeatedly asks Redis:

please rediscover all cache entries derived from this dataset.

That is the architectural smell.

The problem is not only deletion.

The problem is discovery.

Why TTL was not enough

A tempting response is:

do not invalidate anything; just use a short TTL.

That moves the problem rather than solving it.

Suppose the TTL is five minutes.

A user updates a record.

The database is correct immediately.

The cache can remain stale for almost five minutes.

Now the application may show:

Update API:
success

List API:
old value

From the user’s perspective, the system is inconsistent.

Shortening the TTL reduces the stale window but increases cache churn.

Longer TTL improves hit rates but extends inconsistency.

TTL is useful as a safety mechanism.

I do not want it to be the primary correctness mechanism for data that should become stale immediately after a known mutation.

The application already knows exactly when the dataset changes.

It should use that information.

The key insight: stop deleting old generations

The alternative is version-based caching.

Instead of trying to discover and delete every old cache key, maintain a small version number for the logical dataset.

For example:

cache-version:dev:contacts:tenant-42 = 17

A list request first resolves the current version.

Then the actual cache key includes it:

dev:contacts:tenant-42:v17:list:<queryHash>

For example:

dev:contacts:tenant-42:v17:list:a91f8c

Now suppose a contact changes.

Instead of scanning for:

dev:contacts:tenant-42:*

and deleting every matching key, the write path does:

INCR cache-version:dev:contacts:tenant-42

The version becomes:

18

Every new request now reads or writes:

dev:contacts:tenant-42:v18:list:<queryHash>

The old generation still physically exists:

v17

but it is logically unreachable.

That is the entire idea.

No wildcard deletion.

No key discovery.

No synchronous scan.

No need to know how many query variants existed.

One small metadata change invalidates the whole logical namespace.

Before and after

The old invalidation model:

WRITE
│
▼
Update database
│
▼
SCAN Redis keyspace
│
▼
Find matching keys
│
▼
Delete batches
│
▼
Finish request / invalidation

The versioned model:

WRITE
│
▼
Update database
│
▼
INCR dataset version
│
▼
Done

That is a major simplification of the invalidation path.

The complexity moves from:

find and delete every stale cache entry

to:

advance the namespace generation

A concrete example

Assume a tenant requests:

GET /contacts?page=1&status=active

The application canonicalizes the query:

{
"page": 1,
"status": "active"
}

Then computes a stable hash:

queryHash = 7f31a9

The current version is:

17

The final key becomes:

prod:contacts:tenant-42:v17:list:7f31a9

Another request arrives:

GET /contacts?page=2&status=active

Its key may be:

prod:contacts:tenant-42:v17:list:c82d11

Another:

GET /contacts?ownerId=u123&sort=createdAt:desc

becomes:

prod:contacts:tenant-42:v17:list:e51ab0

Now a contact is created.

The write path does not need to know that three cached query variants exist.

It does:

INCR cache-version:prod:contacts:tenant-42

The version is now:

18

The next request uses:

prod:contacts:tenant-42:v18:list:7f31a9

The old key:

prod:contacts:tenant-42:v17:list:7f31a9

cannot be hit by the new read path.

From the application’s perspective, invalidation is immediate.

The read path

Conceptually:

async function getContacts(
tenantId: string,
query: ContactQuery,
) {
const versionKey =
`cache-version:prod:contacts:${tenantId}`;

const version =
(await redis.get(versionKey)) ?? '1';

const queryHash =
createStableHash(normalizeQuery(query));

const cacheKey =
`prod:contacts:${tenantId}:v${version}:list:${queryHash}`;

const cached =
await redis.get(cacheKey);

if (cached) {
return JSON.parse(cached);
}

const result =
await contactsRepository.find(query);

await redis.set(
cacheKey,
JSON.stringify(result),
'EX',
900,
);

return result;
}

The exact implementation can vary.

The important properties are:

  • deterministic query normalization
  • stable hashing
  • tenant isolation
  • module isolation
  • version in the namespace
  • TTL on generated cache entries

The write path

After a successful database mutation:

async function updateContact(
tenantId: string,
contactId: string,
input: UpdateContactInput,
) {
const updated =
await contactsRepository.update(
contactId,
input,
);

await redis.incr(
`cache-version:prod:contacts:${tenantId}`,
);

return updated;
}

The ordering matters.

I prefer:

1. write source of truth
2. invalidate derived cache

not:

1. invalidate cache
2. attempt database write

If the database write fails after invalidation, correctness is usually preserved but the cache was unnecessarily destroyed.

More importantly, the cache should never be treated as the source of truth.

Why the version must be scoped correctly

A global version such as:

contacts:version = 18

would mean one tenant updating one contact invalidates contact caches for every tenant.

That defeats multi-tenant isolation.

The version should be scoped to the smallest useful invalidation boundary.

For example:

cache-version:{env}:{service}:{tenant}:{module}

Such as:

cache-version:prod:crm:tenant-42:contacts

This aligns with the broader cache namespace strategy we discussed:

{env}:{service}:{tenant}:{module}:{hash}

Versioning extends it:

{env}:{service}:{tenant}:{module}:v{version}:{hash}

Now:

  • dev does not invalidate prod
  • one service does not accidentally own another service’s cache
  • one tenant does not invalidate another tenant
  • one module does not invalidate unrelated modules

The invalidation boundary is explicit in the key.

Old generations still need cleanup

Version-based invalidation makes old keys unreachable.

It does not physically delete them immediately.

That is intentional.

Old generation keys should still have TTLs.

For example:

v17 keys → expire naturally
v18 keys → current generation

The model becomes:

Version bump = correctness
TTL = garbage collection

This is a much better use of TTL.

TTL no longer determines how long users see stale data.

It determines how long unreachable cache generations consume memory.

That separation is one of the main reasons I prefer this pattern.

This also helps with timeout behavior

The invalidation problem that motivated this design was not theoretical.

When a request path has to discover and remove many keys, invalidation time becomes dependent on:

  • total keyspace size
  • number of matching keys
  • SCAN iterations
  • Redis round trips
  • delete batch sizes
  • network latency
  • concurrent Redis workload

That means a mutation that should be predictable can become increasingly slow as the cache grows.

Eventually, the application can spend enough time invalidating cache entries that the operation contributes to request timeouts or visibly slow responses.

Version bumping changes the complexity profile.

The invalidation path no longer grows with the number of cached query variants.

Conceptually:

10 cached variants
100 cached variants
10,000 cached variants

all require the same logical action:

INCR version

I am deliberately not claiming a fake benchmark here.

The architectural improvement is the important part:

invalidation no longer requires enumerating the stale cache population.

Multi-instance services become easier to reason about

Suppose the NestJS service runs on multiple instances:

Instance A
Instance B
Instance C

All of them share Redis.

Instance A updates a contact and increments:

tenant-42 contacts version:
17 → 18

Instance B’s next request resolves version 18.

Instance C’s next request resolves version 18.

No instance needs an in-memory list of deleted keys.

No instance needs to know which process originally populated the old entries.

The version stored in Redis becomes the shared generation pointer.

That is a clean coordination primitive.

Cross-service invalidation still requires ownership

Versioning does not mean every service should mutate every cache namespace.

I prefer explicit ownership.

For example:

Contacts Service
owns contact cache

Search Service
owns search cache

Policy Service
owns policy cache

If one domain change affects another service, the change can be propagated as an event:

contact.updated
role.changed
hierarchy.changed
sharing-rule.changed

The receiving service decides how its own cache should react.

That can be:

increment version

or a more targeted invalidation.

This preserves service boundaries.

A service should not need intimate knowledge of another service’s internal Redis key format.

Versioning is not always the right granularity

A version can invalidate too much if the namespace is too broad.

Suppose one tenant has millions of independent records and only one detail cache changes.

Bumping the entire module version may cause unnecessary cache misses.

So I separate cache types by their dependency boundaries.

For example:

List cache:
tenant-wide module version

Detail cache:
direct key invalidation by record ID

Policy cache:
version based on policy dependency

Hierarchy cache:
version based on hierarchy changes

A possible design is:

contacts:list-version:tenant-42
contacts:detail:tenant-42:contact-99

After updating contact 99:

DEL contacts:detail:tenant-42:contact-99
INCR contacts:list-version:tenant-42

That is often better than forcing every cache into one strategy.

The goal is not “version everything”.

The goal is:

choose an invalidation boundary that matches the dependency graph of the cached data.

Authorization caches made this lesson even clearer

The same principle appears in policy caching.

We previously separated authorization-related caches into different logical components:

user:{id}:permissions
user:{id}:subordinates
user:{id}:sharingRules

Why?

Because they change for different reasons.

A role permission update should not force hierarchy reconstruction.

A hierarchy update should not force role permission recomputation.

A sharing-rule change should not invalidate unrelated static permission data.

Versioning can follow the same model.

Conceptually:

permission-version:{tenant}:{user}
hierarchy-version:{tenant}:{user}
sharing-version:{tenant}:{user}

The exact key structure depends on the service.

The broader lesson is that cache invalidation should follow causal dependencies.

Not convenience.

The failure mode I wanted to avoid

The worst cache architecture is one where writes become slower as the cache becomes more successful.

That can happen surprisingly easily.

More reads create more cached query variants.

More cached variants make invalidation more expensive.

More expensive invalidation slows writes.

Slow writes trigger timeouts.

Timeouts trigger retries.

Retries create more pressure.

The cache that was introduced to reduce database load starts increasing system complexity and write latency.

Version-based invalidation breaks that relationship for broad logical datasets.

The number of old keys can grow temporarily, but invalidation itself does not need to enumerate them.

TTL handles cleanup later.

What I kept from the earlier approach

I do not consider SCAN useless.

It remains useful for:

  • operational cleanup
  • migrations
  • administrative maintenance
  • removing known legacy namespaces
  • exceptional background jobs

And if pattern invalidation is necessary, SCAN MATCH ... COUNT ... is far safer than KEYS.

But I no longer want broad pattern scanning in a latency-sensitive write path when the actual requirement is simply:

make every previously cached representation of this logical dataset stale now.

That is exactly what a version number expresses.

The final model

The resulting cache architecture is straightforward:

READ
│
▼
Get logical version
│
▼
Build versioned key
│
▼
Check Redis
│
├── hit ──► return
│
└── miss
│
▼
Database
│
▼
Cache with TTL
│
▼
Return

And writes:

WRITE
│
▼
Update database
│
▼
Increment logical version
│
▼
Return

Old generations:

v15 ──► unreachable ──► TTL cleanup
v16 ──► unreachable ──► TTL cleanup
v17 ──► current

No cache-busting scan is required in the critical path.

The lesson

Cache invalidation becomes difficult when the system tries to track every physical cache entry derived from mutable data.

A different way to frame the problem is:

do I actually need to delete stale keys, or do I only need to make them impossible to read?

Version-based caching chooses the second option.

That shift turned invalidation from a discovery problem into a namespace problem.

Instead of:

find everything stale
then delete it

the system does:

advance the generation

For the timeout and latency problems we were facing around broad invalidation, that is the part that mattered most.

TTL still exists.

Redis still stores multiple query variants.

Old keys still need eventual cleanup.

But correctness no longer waits for a scan to finish.

And the write path no longer needs to know how many cached representations of the old data exist.

Sometimes the simplest invalidation strategy is not deleting more efficiently.

It is making deletion unnecessary.
