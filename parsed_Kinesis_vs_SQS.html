Why I chose Kinesis over SQS for the messaging pipeline

Tag: Architecture
Read time: 7 min

SQS is usually the first AWS service I consider when I need to move work out of a synchronous request path.

It is simple, durable, scalable, and operationally boring in the best possible way. A producer sends a message, a consumer processes it, and the queue absorbs temporary differences in throughput.

For many systems, that is exactly what I want.

But while designing Pulse — an omnichannel, AI-first messaging platform handling channels such as WhatsApp, Facebook Messenger, Instagram DM, and Web Chat — I ran into a constraint that changed the decision:

messages belonging to the same conversation had to be processed in order.

That sounds obvious until the system becomes asynchronous.

A conversation is not just a collection of independent jobs. It is an ordered state transition.

Consider a simple sequence:

10:00:01 Customer sends message A
10:00:02 Customer sends message B
10:00:03 Agent sends reply C
10:00:04 Provider reports C as delivered
10:00:05 Provider reports C as read

If those events are processed out of order, the database can temporarily — or permanently — represent a state that never existed.

A read receipt may arrive before the corresponding outbound message has been reconciled. An AI consumer may generate a reply using stale conversation context. A WebSocket event may show message B before message A. A retry may overwrite a newer status with an older one.

The requirement was therefore not:

process every message globally in order.

That would be expensive and unnecessary.

The actual requirement was:

preserve ordering inside the smallest domain boundary where ordering matters.

For Pulse, that boundary is primarily the conversation.

That requirement is what pushed the architecture toward Amazon Kinesis.

The system I was actually designing

Pulse owns the messaging domain around:

  • contacts
  • conversations
  • messages
  • inbound channel events
  • outbound messages
  • delivery and read statuses
  • real-time agent updates
  • asynchronous AI processing

MongoDB stores the domain state.

NestJS services handle the backend processing.

Socket.IO already provides real-time communication to the application, so I deliberately avoided introducing a second WebSocket architecture through API Gateway WebSocket APIs. Running two independent real-time systems would have created additional connection management, authentication, scaling, and operational overhead.

The asynchronous path needed to support multiple external transports while keeping the internal domain consistent.

At a high level:

WhatsApp ───────────┐
Messenger ──────────┤
Instagram DM ───────┤
Web Chat ───────────┘
│
▼
Channel-specific adapters
│
▼
Event ingestion
│
▼
Kinesis
│
▼
Normalization / enrichment
│
▼
Conversation processing
│
┌─────────┴─────────┐
▼ ▼
MongoDB Socket.IO
│
▼
Async AI consumers

The important architectural principle is that channel-specific payloads should not leak throughout the system.

WhatsApp has one event structure. Instagram has another. Messenger has another. Web Chat is under our own control.

Internally, they are normalized into a common Pulse message model.

Conceptually:

interface PulseMessage {
tenantId: string;
conversationId: string;
channel: 'whatsapp' | 'messenger' | 'instagram' | 'webchat';
direction: 'inbound' | 'outbound';
senderId: string;
recipientId: string;
type: 'text' | 'image' | 'document' | 'audio' | 'video';
content: unknown;
occurredAt: string;
}

This gives downstream consumers a stable contract regardless of the original provider.

But normalization alone does not solve ordering.

The partitioning strategy does.

Why plain SQS was not enough

Standard SQS gives excellent scalability and durability, but strict ordering is not its core guarantee.

For independent background jobs, that is fine.

For conversation state, it is not.

Suppose the customer sends:

A: "I was charged twice"
B: "The second transaction is TX-9281"

If parallel consumers process B before A, several things can go wrong.

The UI can display the messages incorrectly.

An AI consumer can evaluate B without the context established by A.

Conversation metadata such as lastMessageAt or preview text can be updated inconsistently.

Automation rules can run against an incomplete sequence.

The obvious response is to use SQS FIFO.

That is a valid option, and I did not reject it because it is bad technology. I rejected the idea of treating the pipeline as a simple queue because the broader architecture was becoming an ordered event stream with multiple independent consumers.

Pulse needed more than one worker taking jobs from a queue.

The same message lifecycle could feed:

  • persistence
  • real-time delivery
  • AI decisioning
  • analytics
  • audit processing
  • indexing
  • future automation consumers

That distinction matters.

A queue primarily asks:

who should process this job?

A stream architecture also asks:

which consumers need to independently observe this event sequence?

For Pulse, the second question became increasingly important.

The real reason Kinesis fit: partition-local ordering

Kinesis provides ordering within a shard.

The partition key determines how records are distributed.

That means the architecture can intentionally place related events into the same ordered path.

Once a conversation is known, the natural key is:

partitionKey = conversationId

Conceptually:

await kinesis.send(
new PutRecordCommand({
StreamName: 'pulse-message-stream',
PartitionKey: conversationId,
Data: Buffer.from(JSON.stringify(event)),
}),
);

Now imagine three conversations:

Conversation A
A1 → A2 → A3

Conversation B
B1 → B2

Conversation C
C1 → C2 → C3

The system does not require this:

A1 → B1 → C1 → A2 → C2 → B2 → A3 → C3

There is no business value in globally ordering unrelated conversations.

What matters is:

A1 → A2 → A3
B1 → B2
C1 → C2 → C3

Each conversation maintains its own order while unrelated conversations can scale independently.

That is the key tradeoff.

Global ordering would reduce concurrency. No ordering would weaken correctness. Conversation-level partitioning gives the system the ordering boundary it actually needs.

The bootstrap problem: what if the conversation does not exist yet?

There is an important complication.

An inbound webhook does not always arrive with an internal Pulse conversationId.

A provider may send:

  • tenant-related channel information
  • external sender ID
  • page or phone number ID
  • provider message ID
  • channel-specific metadata

But conversationId is an internal domain identifier.

So the ingress path cannot always immediately use:

partitionKey = conversationId

This led to a two-phase ingestion design.

Phase 1: raw ingress

The webhook path should remain fast.

I did not want every provider webhook to perform multiple database operations before acknowledging the request.

The ingress layer therefore accepts the external event and publishes a raw event using a stable source-oriented partition key such as:

tenantId + sourceId

For example:

tenant-42:whatsapp-phone-17

The raw path looks like this:

Provider Webhook
│
▼
Validate request
│
▼
Build raw event envelope
│
▼
Kinesis
Partition: tenantId + sourceId
│
▼
Return acknowledgement

The goal is to keep ingress close to O(1) with respect to application-side domain work.

No conversation reconstruction.

No AI processing.

No expensive fan-out.

No unnecessary synchronous dependency chain.

Phase 2: enrichment and conversation resolution

A downstream consumer takes the raw event and resolves the internal domain context.

It can:

  1. identify the tenant
  2. identify the channel account
  3. resolve the contact
  4. find or create the conversation
  5. normalize the provider payload
  6. emit the enriched event downstream

At that point, the system knows the actual conversationId.

The enriched event can then use:

partitionKey = conversationId

The architecture becomes:

External Provider
│
▼
Webhook Ingress
│
▼
Raw Event Stream
partition: tenantId + sourceId
│
▼
Enrichment Consumer
│
├── resolve contact
├── resolve/create conversation
└── normalize payload
│
▼
Normalized Message Stream
partition: conversationId
│
▼
Domain Consumers

This separation solved two different problems with two different keys.

The raw ingress stage needs stable ordering before the internal conversation exists.

The domain stage needs conversation-local ordering after enrichment.

Trying to force one partitioning strategy onto both phases would have made the design weaker.

Why I did not put database work in the webhook

It is tempting to write:

Webhook
→ query tenant
→ query channel
→ query contact
→ query conversation
→ create conversation if missing
→ insert message
→ invoke AI
→ emit WebSocket event
→ return 200

It is also a fragile request path.

Every dependency increases latency and creates another failure mode.

If MongoDB slows down, webhook acknowledgement slows down.

If AI processing slows down, webhook acknowledgement slows down.

If a downstream service times out, the provider may retry an event that was partially processed.

That creates duplicate handling and more reconciliation work.

The ingestion boundary should therefore do as little domain work as possible.

The stream absorbs the event first.

Domain processing happens asynchronously.

Outbound messages created another ordering problem

Inbound messages are only half the system.

An agent can send an outbound message through Pulse before the external provider assigns its final platform message ID.

For example, Pulse may create:

internal_message_id = msg_123
client_ref_id = ref_abc
platform_message_id = null

The outbound adapter sends the message to the provider.

Later, the provider returns or echoes a platform-specific identifier such as a WhatsApp message ID.

The system then reconciles:

client_ref_id: ref_abc
│
▼
internal_message_id: msg_123
│
▼
platform_message_id: wamid....

After that, delivery lifecycle events may arrive:

sent
↓
delivered
↓
read

These are not independent jobs.

They are state transitions on the same logical message.

That strengthened the case for an ordered event pipeline.

The same inbound/status flow can process later provider events and update the existing message rather than creating disconnected records.

AI had to remain asynchronous

Pulse is AI-first, but I deliberately did not put AI generation in the critical delivery path.

The flow is closer to:

Inbound Message
│
▼
Persist message
│
├──────────────► Real-time agent update
│
▼
AI decision consumer
│
├── should AI respond?
├── is automation enabled?
├── does an agent own the conversation?
└── what context is required?
│
▼
Generate response
│
▼
Outbound event stream

This is important for both reliability and latency.

If an LLM provider is slow, inbound message persistence should still succeed.

If AI generation fails, the conversation should still exist.

If an agent takes over, AI behavior should be controlled by domain state rather than being hardwired into webhook processing.

The stream architecture gives AI its own consumption path without turning it into a blocking dependency.

Kinesis did not remove the need for idempotency

Ordering is not exactly-once processing.

That distinction matters.

A distributed messaging pipeline still needs to assume:

  • retries happen
  • consumers restart
  • providers resend webhooks
  • processing can fail after a side effect
  • the same logical event can be observed more than once

So consumers must remain idempotent.

For provider-originated events, a useful deduplication boundary is the external message or event ID.

Conceptually:

tenantId + channel + providerMessageId

Before creating a new message, the consumer can determine whether the logical event has already been applied.

The principle is simple:

Kinesis gives me an ordering primitive. It does not eliminate duplicate processing semantics.

That is an application responsibility.

Partition keys are a scaling decision, not just an ordering decision

Using conversationId has a consequence.

A very hot conversation can become a hot partition.

That is the tradeoff of preserving strict ordering for that conversation.

But the alternative — distributing messages from the same conversation randomly — would improve parallelism by sacrificing the exact guarantee the architecture needs.

The correct question is therefore not:

which partition key distributes traffic most evenly?

It is:

what is the smallest key that preserves the business ordering requirement while still allowing unrelated work to run concurrently?

For Pulse, conversation-level partitioning is a strong fit because most conversations are naturally independent.

A tenant-level key would be too coarse:

partitionKey = tenantId

One busy tenant could serialize a huge amount of unrelated conversation traffic.

A random key would be too loose:

partitionKey = randomUUID()

It would destroy conversation ordering.

conversationId sits between those extremes.

Why not make Pulse handle everything synchronously?

Because domain ownership and execution coupling are different things.

Pulse can own:

  • contacts
  • conversations
  • messages
  • message lifecycle
  • channel normalization

without requiring every operation to execute synchronously inside one request.

Similarly, I chose to retain the existing NestJS + Socket.IO real-time layer instead of adding API Gateway WebSockets on top of it.

The system already had one real-time mechanism.

Adding another would mean:

  • two connection models
  • two authentication flows
  • two scaling models
  • duplicated event routing concerns
  • more operational complexity

For horizontally scaled Socket.IO instances, Redis can be used as the adapter layer so events reach clients regardless of which application instance owns the connection.

That keeps the architecture focused:

Kinesis = asynchronous ordered event backbone
MongoDB = durable domain state
Socket.IO = real-time client delivery
Redis = Socket.IO scaling / coordination where required
NestJS = domain and processing services
Next.js = agent-facing application

Each component has a clear responsibility.

The tradeoff I accepted

Kinesis is not automatically better than SQS.

It is more operationally involved than a simple queue.

Consumers need to understand:

  • shards
  • partition keys
  • checkpoints
  • replay
  • iterator behavior
  • throughput distribution
  • hot partitions
  • consumer lag

A bad partition key can create a bad system.

A consumer that assumes exactly-once execution can corrupt state.

A stream retained without a replay strategy is wasted complexity.

So I would not choose Kinesis just because the system uses the word “event-driven”.

I chose it because Pulse had a combination of requirements that aligned with an ordered stream:

  • conversation-local ordering
  • independent downstream consumers
  • omnichannel normalization
  • asynchronous AI processing
  • lifecycle events for messages
  • replayable processing
  • high concurrency across unrelated conversations

The decisive constraint was ordering.

The broader event model made the choice worthwhile.

The architecture lesson

The most useful part of this decision was not “Kinesis is better than SQS”.

It was learning to define ordering precisely.

“Messages must be ordered” is too vague.

A better set of questions is:

  • ordered globally?
  • ordered per tenant?
  • ordered per channel account?
  • ordered per contact?
  • ordered per conversation?
  • ordered only after enrichment?
  • what happens before the internal entity exists?

Once I answered those questions, the architecture became much clearer.

For Pulse, the final principle was:

ingest quickly, resolve domain context asynchronously, normalize channel events, then preserve ordering at the conversation boundary.

SQS remains an excellent default.

Kinesis became the right choice only because the messaging domain had an ordering constraint that was both real and precisely defined.

That is the difference between choosing infrastructure by popularity and choosing it from the invariants of the system.
