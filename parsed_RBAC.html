Designing a RBAC system that doesn’t lie to your users

Tag: Systems
Read time: 5 min

Most RBAC implementations look clean in a diagram.

A user has a role.

A role has permissions.

An API checks the permission.

Done.

That model works until someone asks a more realistic question:

The user can read contacts — but which contacts?

That one question changes the problem completely.

In SalesAstra, access is not only about whether an action is allowed. It is also about the scope within which that action is allowed.

A user may be able to:

  • view only their own records
  • view records owned by members of their team
  • view records visible through hierarchy
  • view records explicitly shared with them
  • view records exposed by sharing rules
  • view every record in the tenant

At that point, a boolean permission is no longer enough.

This:

{
"contacts.read": true
}

is technically valid and operationally misleading.

It tells the application that the user can read contacts.

It says nothing about which contacts.

That is how authorization systems start lying to users.

The UI shows a module because the permission says “allowed”. The list API returns fewer records because another visibility rule exists somewhere else. A search endpoint returns records that the normal list endpoint hides. One microservice interprets “team” differently from another.

The user experiences inconsistent behavior even though every individual service believes it is enforcing permissions correctly.

I wanted to avoid that.

The architecture I settled on separates two concerns that are often incorrectly merged:

  1. What actions can this user perform?
  2. Which records are visible to this user?

That distinction became the foundation of the policy layer.

Permission is not visibility

The role system defines action capability.

For example:

{
"module": "contacts",
"action": "read",
"allowed": true,
"scope": 2
}

In our model, scope values represent boundaries such as:

1 → own / self
2 → team / group
3 → all / any

The exact labels matter less than the principle.

A role can say:

contacts.read = allowed, scope = team

But the role should not permanently store an expanded list such as:

{
"accessibleUserIds": [
"u1",
"u2",
"u3",
"u4",
"u5"
]
}

Why?

Because that list is not actually role data.

It is derived from mutable organizational state.

It can change when:

  • a manager changes
  • a user moves to another team
  • hierarchy changes
  • a sharing rule changes
  • team membership changes
  • a role assignment changes
  • an explicit sharing relationship changes

So I kept action permissions in RBAC and treated hierarchy and sharing as visibility inputs.

That gives a much cleaner separation:

Role permissions
│
├── can read?
├── can create?
├── can edit?
└── can delete?

Visibility model
│
├── self
├── team
├── hierarchy
├── sharing rules
└── tenant-wide

A manager seeing a subordinate’s record does not automatically mean the manager can edit or delete it.

Visibility answers:

can this record participate in the user’s accessible dataset?

Action permission answers:

what operation may the user perform?

Those are related questions, but they are not the same question.

Why I centralized policy evaluation

SalesAstra is composed of multiple services.

Without a centralized policy model, every service eventually implements its own interpretation of access.

The Contacts service may write:

if (user.role === 'manager') {
// include team
}

The Leads service may write:

if (scope === 2) {
// include direct reports
}

The Search service may write:

if (user.isAdmin) {
// bypass filters
}

Now there are three authorization systems.

They may share terminology, but they do not share semantics.

That is dangerous because permission bugs are often not obvious denials. They are inconsistencies.

A user can find a record in global search but cannot open it.

A dashboard counts records that the list API does not show.

An export includes data hidden in the UI.

One endpoint interprets team scope as direct reports. Another includes the full subordinate tree.

To avoid that, we already designed a centralized policy endpoint that resolves the effective access context.

Conceptually:

POST /permissions/evaluate

or a policy-oriented endpoint with inputs such as:

{
"userId": "user-123",
"tenantId": "tenant-456",
"module": "contacts",
"action": "read"
}

The policy layer resolves the context required by downstream services.

Conceptually:

{
"allowed": true,
"scope": 2,
"visibility": {
"self": true,
"eligibleUserIds": [
"user-123",
"user-201",
"user-202"
]
}
}

The exact response can evolve.

The important point is ownership:

hierarchy, team membership, scope interpretation, and sharing-rule resolution belong to the policy domain rather than being independently reinvented inside every module service.

The request path

Authentication establishes identity.

Authorization establishes what that identity can do.

A typical request arrives with an authorization token.

The service extracts the authenticated subject from claims:

Authorization header
│
▼
Validate token
│
▼
Extract sub
│
▼
Resolve authorization policy
│
▼
Allow / deny
│
▼
Apply visibility constraints
│
▼
Execute operation

The sub claim identifies the authenticated user.

The service should not trust a client-provided body field such as:

{
"userId": "someone-else"
}

for authorization identity.

The authenticated principal comes from the verified token context.

Conceptually:

const subjectId = req.user.sub;

The service then evaluates whether that subject can perform the requested action.

For example:

contacts.read
leads.update
accounts.delete
support-cases.assign

The backend enforces the result.

The frontend may hide buttons for usability, but hidden UI is not authorization.

Scope changes the query, not just the response code

One of the most important design decisions was that scope should influence the database query itself.

Suppose a user requests:

GET /contacts

A weak implementation does this:

1. query all tenant contacts
2. load them into memory
3. remove unauthorized records
4. return the remainder

That is inefficient and dangerous.

The better model is:

Policy context
│
▼
Build authorized query
│
▼
Database

For own scope:

{
tenantId,
ownerId: subjectId
}

For team or hierarchy scope:

{
tenantId,
ownerId: {
$in: eligibleUserIds
}
}

For all scope:

{
tenantId
}

Sharing can extend the visibility predicate:

{
tenantId,
$or: [
{ ownerId: { $in: eligibleUserIds } },
{ sharedWithUserIds: subjectId },
{ teamId: { $in: eligibleTeamIds } }
]
}

The exact persistence model depends on the module, but the principle stays the same:

authorization should constrain the data retrieval boundary, not merely filter data after retrieval.

Hierarchy is a graph problem hiding inside an RBAC problem

Roles are relatively static.

Hierarchy is not.

Imagine:

VP
├── Manager A
│ ├── User A1
│ └── User A2
└── Manager B
├── User B1
└── User B2

Now ask:

What does team scope mean for the VP?

Possible interpretations include:

  • only direct reports
  • all descendants
  • members of explicitly assigned teams
  • descendants plus shared records
  • descendants only for selected modules

There is no universally correct answer.

The policy model must define it.

The important architectural decision is that module services should not each traverse the hierarchy independently.

If they do, one service will eventually include direct reports while another includes the full subtree.

So the policy layer resolves the eligible user set according to one consistent definition.

Conceptually:

User
│
▼
Role + Scope
│
▼
Hierarchy Resolver
│
├── direct reports
└── descendant subtree
│
▼
Team Resolver
│
▼
Sharing Rule Resolver
│
▼
Effective Visibility Context

This is why I think of the system as graph-based authorization even though the user-facing model still looks like RBAC.

RBAC answers the action.

The graph resolves reachability.

Sharing rules complicate everything

Hierarchy alone is manageable.

Sharing rules introduce non-hierarchical edges.

Suppose User A belongs to Team East.

User B belongs to Team West.

A sharing rule says:

Opportunities owned by Team East
are visible to Sales Managers in Team West

Now visibility is no longer a tree.

It is a graph.

A record may be visible because of:

  • ownership
  • direct team membership
  • hierarchy
  • role-based sharing
  • team-based sharing
  • explicit sharing
  • tenant-wide scope

That is why I did not want module services to hard-code visibility rules.

The policy layer resolves those relationships and returns a consistent access context.

I deliberately avoided storing final permissions per user

A common optimization is to calculate everything and save:

user → final permissions

I avoided treating that as the source of truth.

Effective access is derived from multiple changing inputs:

User
+ role assignments
+ role permissions
+ scope
+ hierarchy
+ team membership
+ sharing rules
= effective access

Persisting the final expanded result creates a synchronization problem.

Every change now requires discovering every affected user and rewriting their materialized permissions.

Instead, the source of truth remains normalized.

Derived results can be cached.

That distinction is important:

cache derived authorization state, but do not confuse the cache with the authorization model.

The cache needed to be split by reason for change

One of the better decisions was not caching authorization as one giant object.

A naive key might be:

user:123:everything

That looks convenient until something changes.

If a sharing rule changes, should the entire permission cache be invalidated?

If a hierarchy node moves, should role permissions be recomputed?

If a role gains contacts.export, should the subordinate tree be rebuilt?

Those data sets have different invalidation triggers.

So the model was split conceptually into layers such as:

user:{id}:permissions
user:{id}:subordinates
user:{id}:sharingRules

Now invalidation follows causality.

Role permission change

Invalidate:

user:{id}:permissions

for users affected by the role.

User-role assignment change

Invalidate:

user:{id}:permissions

for the affected user.

Hierarchy change

Invalidate:

user:{id}:subordinates

for managers whose reachable subtree changed.

Sharing-rule change

Invalidate:

user:{id}:sharingRules

for affected users.

Team membership change

Invalidate the visibility-related cache that depends on team membership.

This is much more precise than deleting every authorization key whenever anything changes.

Search exposed whether the model was actually consistent

Global search is where weak authorization designs become obvious.

A normal module endpoint may enforce visibility correctly:

GET /contacts

Then a separate Search service indexes the same contacts and accidentally returns everything in the tenant.

The search result now leaks the existence of unauthorized records.

My decision was not to push a permanently expanded list such as:

{
"accessibleUsers": [
"u1",
"u2",
"u3"
]
}

into every OpenSearch document.

That would couple the search index to mutable authorization topology.

A hierarchy change could require reindexing huge numbers of business records even though the business data itself did not change.

Instead:

Request
│
▼
Search Service
│
▼
Policy Context
│
├── scope
├── eligible users
├── teams
└── sharing visibility
│
▼
Build authorization filters
│
▼
OpenSearch query

Permission changes update policy state.

They do not require rewriting every indexed contact, lead, account, or opportunity.

That separation is critical.

The index stores searchable business facts.

The policy layer determines current visibility.

Event-driven invalidation

Authorization state changes are meaningful domain events.

Examples include:

role.changed
user-role.changed
scope.changed
hierarchy.changed
team.changed
sharing-rule.changed

Those events can invalidate the appropriate cached policy context.

This matters in a microservice architecture because the service making the change may not be the service holding a derived cache.

Without explicit invalidation events, services drift.

One service sees the new hierarchy.

Another continues serving the old team visibility until TTL expiry.

A third has stale search authorization.

That is exactly the kind of system that appears correct in unit tests but behaves inconsistently in production.

Impersonation made the identity model even more important

The same principles become critical when platform administrators can impersonate tenant users.

Our existing service flow relies heavily on the authenticated request context:

token
→ extract sub
→ load permissions/scope
→ authorize action
→ audit using req.user

A naive impersonation implementation simply replaces the subject.

That is dangerous because the system can lose the distinction between:

  • who actually initiated the action
  • whose permissions are being applied

Those are separate identities.

Conceptually:

actor = platform administrator
subject = impersonated tenant user

Authorization may need to execute using the subject’s effective tenant permissions.

Audit must preserve the actor.

Otherwise an administrator could perform an action while the audit trail falsely claims that the tenant user initiated it.

That is not a logging detail.

It is part of the authorization model.

A trustworthy system must be able to answer both:

Who performed the action?

and:

Under whose access context was it executed?

The frontend should not invent authorization

Another rule I kept was:

the frontend consumes authorization; it does not define authorization.

The frontend can use policy results to:

  • hide unavailable actions
  • disable buttons
  • avoid showing inaccessible navigation
  • explain why an action is unavailable

But the API must still enforce the rule.

For example:

UI hides Delete

is a user-experience decision.

API rejects unauthorized DELETE request

is security.

Both are useful.

Only one is authoritative.

What “doesn’t lie to your users” means

A trustworthy authorization system should produce consistent answers across:

  • list APIs
  • detail APIs
  • updates
  • deletes
  • exports
  • dashboards
  • global search
  • background jobs
  • real-time events

If a user cannot access a contact through the Contacts service, global search should not expose it.

If a sharing rule grants visibility, the list endpoint should not continue hiding the record because its local cache is stale.

If a manager loses hierarchy access, the change should not require waiting for an arbitrary TTL before sensitive records disappear.

If an administrator impersonates a user, the audit trail should not erase the administrator’s identity.

That consistency is the real goal.

The architecture I ended up with can be summarized as:

Authentication
│
▼
Authenticated subject
│
▼
Central Policy Evaluation
│
├── role permissions
├── action
├── scope
├── hierarchy
├── teams
└── sharing rules
│
▼
Effective Access Context
│
├────────────► CRUD services
├────────────► Listing queries
├────────────► Search filters
└────────────► UI capability hints

RBAC was only the starting point.

The real system is a combination of capability, scope, and graph-derived visibility.

The biggest lesson was this:

allowed: true is not a complete authorization decision when access depends on which records the user is allowed to see.

Once hierarchy, teams, and sharing enter the system, permissions stop being a table lookup.

They become policy evaluation.

And if every service evaluates that policy differently, the system eventually lies.
